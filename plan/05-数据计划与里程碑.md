## 一、数据资产总览

| 资产 | 目录 | 形态 | 生产者 | 消费者 | 入库里程碑 |
|---|---|---|---|---|---|

| 规则库（依据×版本） | `data/rules/<doc>/<ver>.json` | **冻结产物**（生成器产出，禁手改） | `tools/gen_rulesets.py` | `engine` | M1（M2 扩充：场景门控 + unique） |

| 合成样本 + 真值库 | `data/truth/` | 文件 + JSON | `tools/gen_samples.py` | `benchmark`、测试 | M1（样本）/ **M4（真值库由基准消费，不另造）** |
| **解析通路算例（真容器字节）** | `data/parse/fixtures.json` | JSON（含 base64 容器字节）+ 植入真值 | `tools/gen_parse.py` | `parse` 回归测试、`benchmark` | **M2** |
| 演示资产 | `docs/demo/` | PNG/GIF | `tools/make_demo_assets.py` | README | M5 |

**台账联动纪律**：任一资产入仓 → `data/README.md` 登记（来源 + 许可 + sha256）；二进制入仓 →
脱敏脚本白名单 + 台账 sha256 三处同步。改数据走生成器整目录重生成，配"再生成位级一致"守门测试。

> **解析算例为何用 base64 而非二进制入仓**：`data/**` 是**冻结文本资产**（全仓 EOL 门要求零 CR），
> 而 PNG/JPEG/MP4 的二进制天然可能含 `0x0D` 字节，直接入仓会误触 EOL 门。base64 解码后
> 仍是**真实容器字节**（完整走解析通路），同时保持文本资产口径（也符合"样本只留可复现形态"）。

## 二、规则库入库流程（M1 的核心工作）

```
① 抓原文 → data/knowledge/raw/<doc>/<date>.html（curl 落盘，不用摘要工具转述）
② 人工逐条核对 → 在 ruleset 源模板（tools/rulesets/*.py 中的确定性模板）写条目
   · 每条必须挂：条款号 + 要点摘录 + source_url + verified_at
   · 核对通过 → status="verified"；核不到 → status="pending"（保留，不进引擎）
③ tools/gen_rulesets.py 生成 data/rules/<doc>/<ver>.json（冻结产物，无时间戳、LF）
④ 更新 registry.json 的 sha256 / status / active
⑤ 重跑 tests + bench，确认门控与基准不回退
```

## 三、合成样本生成器设计（M1 建，M4 扩充）

### 3.1 确定性纪律（硬要求）

- **禁 stdlib `random`**（不承诺跨版本序列一致）→ 用 `labelcheck.rng.splitmix64`；
- **禁 set 迭代序**（一律 list + 显式排序）；**禁系统时钟进产物**（时间字段由参数传入）；
- 落盘用 `open(..., "w", newline="\n", encoding="utf-8")`（统一走 `jsonio.write_text_lf`，不依赖平台默认 newline）；
- 生成器 **`--seed` 固定** → 整目录重生成**逐字节一致**（配守门测试）。

### 3.2 真值语义（一次定清，写进生成器模块注释）

每个合成件输出 `{ input_card, expected }`：

```jsonc
{
  "input_card": { …LabelCard… },
  "expected": {
    "grade": "partial",                       // 主期望
    "also_expect": {                          // 同一注入隐含的其余结论
      "implicit_fail_targets": ["content_property"],
      "explicit_fail_targets": []
    },
    "injected": { "defect": "missing_field", "field": "content_property" }
  }
}
```

**对账语义**：评测按 **`expected` 声明的全部非 pass 集合**与引擎输出的非 pass 集合比对（`fail` ∪ `unknown`
的目标集，**未观测的 scope 排除在比较之外**），**单一实现源**（`benchmark/cases.py` 的
`observed_nonpass`/`compare_nonpass`）供测试与基准共用；**不许改真值凑引擎**。

> **M4 落地**：`benchmark.cases` 即上述"单一实现源"。`tests/test_generators.py`
> （标识卡真值库）与 `tests/test_parse_regression.py`（解析算例）已改为**共用**该函数，
> 内置基准 `bench` 亦调用之——三处口径不可能分叉。

### 3.3 缺陷注入枚举（覆盖 01 §二.7 要求）

| 注入 | 说明 | 期望主结论 |
|---|---|---|
| `correct` | 显式 + 隐式全部合规 | compliant |
| `missing_field` | 缺某隐式字段 | partial / non_compliant（按 severity） |
| `wrong_position` | 显式要素位置不在允许集 | partial |
| `wrong_value` | 隐式字段取值越界/不在枚举 | partial |
| `bad_format` | 隐式字段格式不符 pattern | partial |
| `metadata_stripped` | 隐式全缺、显式齐全（**边界情形，01 §三.3 明确要求**） | 按 critical 是否含隐式规则定级 |
| `explicit_only` | 显式齐全、隐式齐全但有一项 minor 缺失 | partial |

### 3.4 数据纪律（红线）

- 样本**全部虚构**：服务提供者用明显虚构值（`示例提供者编码 SYN-0001`），禁止真实平台/真实用户/真实商业内容；
- **不收录真实平台内容**：样本仅留结构与指纹；
- 体量受控：超大样本不入仓，**只留生成参数**（seed + 配置），台账注明。

### 3.5 解析通路算例生成器（M2）

`tools/gen_parse.py` 产出 `data/parse/fixtures.json`：每例 = **真实容器字节**（base64）+ 植入的
「解析可观测性 + 核验结论」真值。构造器 `png_bytes` / `jpeg_bytes` / `mp4_bytes` 与
`tests/test_parse.py` 共用（测试现造字节，不依赖仓库数据）。

**真值语义**：每例声明 `implicit_observed` / `explicit_observed`（解析器据实报告）、`grade`、
两个 scope 的 `fail` 目标集、降级 `reasons`（子集断言）。对账口径与 §3.2 同源。

**覆盖形态**（防"只测 happy path"）：`correct` / `missing_field` / `wrong_value` / `bad_format` /
`metadata_stripped` / `duplicate_label` / `structure_broken`，容器覆盖 PNG/JPEG/ISO BMFF，
载体覆盖 image/video/audio。

**确定性**：容器字节由固定常量构造（无 RNG/时钟）→ 重生成逐字节一致（`--check` 守门）。
