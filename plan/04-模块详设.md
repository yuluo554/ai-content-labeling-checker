> 上游：[03-架构与技术选型.md](03-架构与技术选型.md)。本文件是**实现契约**：M0 骨架与后续里程碑都按此 schema 落地，改这里 = 改口径。

## 一、统一中间表示（UMR）

全部核验器的输入是同一个 **`LabelCard`**（标识卡），输出是同一个 **`CheckReport`**。

### 1.1 `LabelCard`（输入）

```jsonc
{
  "card_id": "SYN-TEXT-0001",          // 必填，件唯一标识
  "carrier": "text",                    // 必填 ∈ {text, image, audio, video}
  "source": "synthetic",                // ∈ {synthetic, manual, parsed}
  "scenario": "authored",               // M2 新增 ∈ {authored, exported, propagated}
  "observed": { "explicit": true, "implicit": true },   // M2 新增：该 scope 是否被观测到
  "content_sha256": "<64 hex>",         // 必填，内容指纹（证据链）
  "explicit": [                         // 显式标识要素（人工录入或解析产出）
    { "element": "text_explicit_notice", "present": true,
      "position": "head", "text_excerpt": "……（≤80 字）" }
  ],
  "implicit": {                         // 隐式标识字段字典（容器元数据键值，未归一）
    "AIGC:Label": "1",
    "AIGC:ContentProducer": "示例提供者"
  },
  "implicit_duplicate_keys": [],        // M2 新增：被观测到出现多次的容器键（§6.1 c)）
  "notes": ""                           // 可选，人工备注；不参与判定
}
```

**纪律**：
- `explicit[].present = false` 时 `position`/`text_excerpt` 应缺省；`present = true` 而无 `position` →
  判定为 `unknown`（不予臆测合规）。
- `implicit` 的键是**容器/元数据原始键**，归一由映射引擎负责（§五）。
- `content_sha256` 缺失或不合法（非 64 hex）→ 整件判 `invalid_input`，不进判定路径（避免证据链断裂的假结论）。
- **`scenario`**（M2）：适用场景，见 §五.4。缺省 `authored`。
- **`observed`**（M2）：哪一 scope 的数据**确实被观测到**。解析通路对 `explicit` 恒为
  `false`（文件解析器看不到渲染后的文字/语音）；该 scope 全部规则判 `unknown`。
- **`implicit_duplicate_keys`**（M2）：字典形态看不见"同一容器键出现多次"，由解析通路
  据实登记，供 `unique` 规则判 §6.1 c) 的"仅保留一份"。

### 1.2 `CheckReport`（输出）

```jsonc
{
  "card_id": "...", "carrier": "text",
  "ruleset": {                          // 规则库坐标（报告头固定输出）
    "coordinate": "labeling-measures@2025-09-01+gb45438-2025@2025-09-01",
    "documents": [ { "doc_id": "gb45438-2025", "version": "2025-09-01", "sha256": "..." } ],
    "verified_rule_count": 0, "pending_rule_count": 12
  },
  "explicit":  [ Finding… ],
  "implicit":  [ Finding… ],
  "grade": "partial",                   // §六 分级
  "missing": [ "…" ], "errors": [ "…" ],
  "disclaimer": "本核查结论供参考，正式合规认定以监管口径为准。"
}
```

### 1.3 `Finding`（逐要素/逐字段判定）

```jsonc
{
  "scope": "explicit",                  // explicit | implicit
  "target": "text_explicit_notice",     // 要素 id 或国标字段名
  "status": "pass",                     // pass | fail | unknown | skipped
  "severity": "major",                  // critical | major | minor
  "scenario": "authored",               // M2 新增：本条判定所作的适用场景
  "code": "position_not_allowed",       // 机器可读原因码（见 §四/§五）
  "message": "…",
  "clause": { "doc_id": "…", "version": "…", "article": "…", "status": "verified" },
  "evidence": { "observed": "…", "expected": "…" }
}
```

**`status` 语义（定稿，不许漂移）**：
| 值 | 含义 | 是否计入违规 |
|---|---|---|
| `pass` | 明确合规 | 否 |
| `fail` | 明确不合规 | 是 |
| `unknown` | 输入不足以判定（缺字段但规则要求、解析失败、**该 scope 未被观测**） | **否**，但计入"待人工确认"清单 |
| `skipped` | 该规则对本地不适用（载体不匹配 / 场景门控未过） | 否 |

> `unknown ≠ fail`：这是"不给用户假合规结论"与"不冤枉用户"的平衡点。
> `skipped ≠ pass`：**不适用**不等于**合规**——分级时 `skipped` 不参与（见 §六）。

### 1.4 报告新增字段（M2）

`CheckReport` 新增 `source` / `scenario` / `observed`（透传输入），`--json` 输出另有
`parse` 块（仅解析通路）：`{container, implicit_observed, explicit_observed,
aigc_field_count, payload_count, reasons}`——把"解析到什么、降级为什么"一并留痕。

## 二、CLI 与退出码（锁进测试）

### 2.1 子命令

| 命令 | 作用 | 状态 |
|---|---|---|
| `labelcheck check <card.json \| FILE>` | 单件核验（标识卡 JSON **或容器文件**，M2）；`--json` 输出机器可读报告 | ✅ 实现 |
| `labelcheck parse <FILE>` | 解析容器文件 → 标识卡（`--json` / `--out PATH`）；M2 新增 | ✅ 实现 |
| `labelcheck scan <DIR\|MANIFEST>` | 批量扫描 + 报告导出 + 两轮对账（`--out` / `--json` / `--baseline` / `--progress-every` / `--quiet`）；M3 | ✅ 实现 |
| `labelcheck bench` | 运行内置评测基准（三类；`--only` / `--json` / `-v`） | ✅ 实现（M4） |
| `labelcheck selfcheck` | 自检：数据定位 + 规则库加载 + 版本 + 门控计数 | ✅ 实现 |
| `labelcheck version` | 打印版本与规则库坐标 | ✅ 实现 |

全局选项：`--data-dir PATH`（覆盖数据目录）、`-v/--verbose`。
`check` / `parse` / `scan` 另有 `--scenario {authored,exported,propagated}`（覆盖卡内场景，M2/M3）。
`scan` 的 `--generated-at TS` 进报告与对账（**由调用方传入** → 可复现）。
`bench` 另有 `--only NAMES`（逗号分隔，缺省全跑）与 `--json`（M4）。

**`check` 的输入分派（M2）**：先按 JSON 解析；解析失败再按容器魔数（PNG/JPEG/ISO BMFF）
走解析通路；两者皆不是 → 用法错误（exit 2，**不静默给假结论**）。

**`bench` 的退出码（M4）**：`0` 全部达标 / `1` 有基准未达标 / `2` 用法错误（未知基准名）。
与 `check`/`scan` 的 `1 = 检出问题` 语义一致（脚本可按码分流"基准回退"）。

### 2.2 退出码语义（**单一定义源 = `errors.py`**）

| 码 | 含义 |
|---|---|
| `0` | 完成且**未发现 fail**（允许存在 `unknown`；`unknown` 走"降级完成"仍是 0，但 stderr 提示） |
| `1` | 完成但**发现 fail**（核查出不合规）——便于 CI/脚本按码分流 |
| `2` | **用法/输入错误**（参数错、文件不存在、JSON 坏、card 校验失败） |
| `3` | **环境/依赖错误**（规则库缺失、数据目录定位失败、可选依赖缺失需降级） |

> 关键：`check` 的退出码 **1 = 检出不合规**，不是"程序出错"。测试锁死这四条。

### 2.3 输出纪律

- 人类可读输出到 stdout；错误到 stderr；进度到 stderr（便于管道）。
- 入口处 `_ensure_utf8_stdio()`：按 `stream.encoding` 探针决定是否 reconfigure（中文控制台 cp936 不动；
  CI 的 cp1252 才转）——避免 `UnicodeEncodeError`。
- `--json` 模式 stdout **只有 JSON**，供上游程序消费（报告头含规则库坐标 + 免责声明）。

## 三、规则库（版本化 + status 门控）

### 3.1 目录与文件组织

```
data/rules/
├─ registry.json                  # 依据文件注册表（doc_id / 文号 / 版本 / 施行日 / status / sha256）
├─ labeling-measures/2025-09-01.json   # 按「依据文件 × 版本」一份
└─ gb45438-2025/2025-09-01.json
```

### 3.2 `registry.json`

```jsonc
{
  "schema_version": 1,
  "documents": [
    { "doc_id": "labeling-measures",
      "title": "人工智能生成合成内容标识办法",
      "doc_number": "国信办通字〔2025〕2 号",
      "kind": "measure", "issuer": "…",
      "versions": [
        { "version": "2025-09-01", "effective_from": "2025-09-01",
          "rules_file": "labeling-measures/2025-09-01.json",
          "status": "pending",        // verified | pending（整份文件的核对状态）
          "source_url": "https://www.cac.gov.cn/…",
          "sha256": "<文件 hex>" } ] }
  ],
  "active": { "labeling-measures": "2025-09-01", "gb45438-2025": "2025-09-01" }
}
```

- `active` 声明**当前生效版本**（切换口径 = 改这里）。
- `status=pending` 的文档**整份**不得进入判定路径。

### 3.3 单份规则文件 schema

```jsonc
{
  "schema_version": 1,
  "doc_id": "gb45438-2025", "version": "2025-09-01",
  "rules": [
    {
      "rule_id": "gb45438:explicit:text.notice.presence",
      "scope": "explicit",                 // explicit | implicit
      "carrier": ["text"],                 // 适用载体（空 = 全部）
      "target": "text_explicit_notice",    // 显式=要素 id；隐式=国标字段名
      "check_type": "presence",            // 见下方分派表（含 M2 的 unique）
      "params": { "allowed": ["head", "tail"] },
      "severity": "major",                 // critical | major | minor
      "only_if": {                         // 可选门控（类目隔离 + M2 场景画像）
        "carrier": ["text"],
        "scenario": ["propagated"]         // M2：缺省 = 全场景适用
      },
      "clause": { "article": "…", "excerpt": "要点（不全文转载）" },
      "status": "pending",                 // verified | pending  ← 逐条门控
      "source_url": "…", "verified_at": null
    }
  ]
}
```

**`check_type` 语义（引擎按此分派）**：
| check_type | params | 判定 |
|---|---|---|
| `presence` | `{}` | 字段/要素存在且非空 → pass；显式要素 `present=false` → fail；隐式字段缺失 → fail |
| `position` | `allowed: [...]` | 观测位置 ∈ allowed → pass，否则 fail(code=position_not_allowed)；缺位置 → unknown |
| `enum` | `allowed: [...]` | 取值 ∈ allowed → pass，否则 fail(code=value_not_allowed) |
| `pattern` | `regex: "…"` | 全匹配 → pass，否则 fail(code=format_mismatch) |
| `type` | `expect: "string"\|"int"\|…` | 类型匹配 → pass，否则 fail(code=type_mismatch) |
| `range` | `min`/`max`（数值，可省一端） | 在范围内 → pass，否则 fail(code=value_out_of_range) |
| `unique`（M2） | `{}` | 需**整块隐式标识**上下文：同一要素被多容器键/多份载荷重复提供 → fail(code=duplicate_implicit_label)；仅一份 → pass；全无 → unknown。依据 §6.1 c)「应仅保留一份文件元数据隐式标识」。**只许 implicit scope**（加载期强制） |

> `unique` 由 `engine/implicit.py` 直接判定（不经 `evaluate()`）——`evaluate()` 对它显式报错，
> 防止把它误当成逐值分派类型（它需要的是整块上下文，不是单个观测值）。

### 3.4 门控函数（单点）

```python
def effective_ruleset(data_dir) -> Ruleset:
    """只含 status=verified 且文档 status=verified 的规则；其余记入 pending 清单。"""
```

- `Ruleset.pending` 保留未生效条目（供 `selfcheck`/报告展示"还有多少条待核对"）。
- **`pending` 条目绝不参与判定**——这是 NFR-4 的唯一实现点，测试锁死。
- **M0 现状（历史）**：全部条目 `pending` → `effective_ruleset()` 返回**空规则集**，`check` 输出"0 条生效规则、
  全部 unknown/skipped"，**退出码 0**（没查出 fail）。这正是"未核对不得生效"的可观测行为。
- **M1 现状**：GB 45438-2025 已逐条挂原文核对 → 22 条生效；《标识办法》9 条记录法定义务与真实条号、
  保持 `pending`（技术判定与国标同源，由国标承担，避免同一 target 跨文档双份 Finding）。

## 四、显式标识核验（`engine/explicit.py`）

对每条 `scope=explicit` 且载体匹配的规则：

1. 在 `card.explicit[]` 中按 `target` 取要素；不存在 → 按 check_type 判定：
   - `presence` → `fail`(code=`element_absent`)；
   - 其他类型 → `unknown`(code=`element_absent_cannot_verify`)，不臆测。
2. 要素存在但 `present=false` → `fail`(code=`element_not_present`)。
3. `present=true` 且规则为 `position` → 比对 `allowed`；缺 `position` → `unknown`(code=`position_unknown`)。
4. 其余 check_type 按 §三.3 分派（对 `value` 字段）。

**"位置形式"判定（FR-2）就是 `position` check_type**：不只判"有没有"，还判"位置对不对"。

## 五、隐式标识字段核验 + 字段映射（`engine/implicit.py` + `mapping/`）

### 5.1 映射表 `data/mapping/national-fields.json`

```jsonc
{
  "schema_version": 1,
  "fields": [
    { "national_field": "content_property",       // 国标字段名（引擎用）
      "label": "生成合成内容属性信息",
      "aliases": ["content.property", "ai.property", "XMP:Label"],  // 容器键别名
      "status": "pending", "source_url": "…" }
  ],
  "profiles": { "generic_metadata": ["content.property", "…"] }     // 可选：容器画像
}
```

### 5.2 归一算法（确定性，优先级明确）

对每个 `national_field`：
1. 直连命中：`card.implicit` 中存在与 `national_field` 同名的键 → 取之；
2. 别名命中：按 `aliases` **声明顺序**取第一个存在的键（顺序敏感 → 确定性）；
3. 多别名同时命中 → 取**声明序最先**者，其余记入 `evidence.alternatives`（不静默丢弃）；
4. 未命中 → 该字段缺省，由 `presence` 类规则判 `fail`。

**歧义处理**：同一容器键映射到多个国标字段 → 加载期**报错**（映射表自身缺陷，不猜测），退出码 3。

### 5.3 字段核验

对每条 `scope=implicit` 规则，用归一后的值按 check_type 判定；缺失 → `fail`(code=`field_absent`)（`presence`）
或 `unknown`(code=`field_absent_cannot_verify`)（其余类型）。

### 5.4 适用性画像：场景门控与观测作用域（M2）

办法第四条第二款（导出）/第六条（传播平台）与国标 §6.1 a) 4) 5)（传播要素）**只对特定场景成立**。
把"不适用"判成违规会冤枉用户，把它当成"已满足"又是不作为——故引入两个**输入契约**：

| 契约 | 取值 | 语义 | 落到判定 |
|---|---|---|---|
| `scenario` | `authored`（默认）/ `exported` / `propagated` | 本次核验的适用场景 | 规则 `only_if.scenario` 未命中 → **`skipped`**（不是 fail） |
| `observed[scope]` | `true` / `false` | 该 scope 的数据是否**确实被观测到** | `false` → 该 scope 全部判 **`unknown`**（不是 fail，也不是 pass） |

**这是把 M1 的 4 条 `pending` 转 `verified` 的唯一正当路径**：先有适用性画像（决定"对谁适用"），
再据原文核对。M2 据此转 verified 的条目：

| 条目 | 场景门控 | 依据 |
|---|---|---|
| `gb45438:implicit:content_propagator.presence` | `propagated` | §6.1 a) 4)（办法第六条传播平台义务） |
| `gb45438:implicit:propagate_id.presence` | `propagated` | §6.1 a) 5) |
| `measures:explicit:export.file.label.presence` | `exported` | 办法第四条第二款（导出文件须含显式标识） |
| `measures:propagation:platform.hint.presence` | `propagated` | 办法第六条（发布内容周边显著提示） |

**观测作用域与解析通路的配合（关键）**：文件解析只能读元数据，读不到渲染后的显式标识 →
解析通路的卡 `observed.explicit = false` → 显式规则一律 `unknown`（"没查到"≠"没有"）。

**"已观测但确实缺失" vs "未观测"必须区分**（两者都重要）：

- 容器结构完整且配置了解析画像 → 元数据区**已被检查**（`observed.implicit = true`）；
  此时没有 AIGC 载荷 = **该文件确实没有隐式标识** → `presence` 规则判 `fail`；
- 容器结构畸形/截断，或容器类型不可识别 → **未观测**（`observed.implicit = false`）
  → 一律 `unknown`（不臆测）。

## 五之二、解析通路（`parse/`，M2）

**定位**：可解析容器文件 → 同一 UMR（`LabelCard`），交给引擎走与手工录入**完全相同**的判定路径。

| 容器 | 载体 | 抽取位置 |
|---|---|---|
| PNG | image | `tEXt` / `zTXt` / `iTXt` 文本块 |
| JPEG | image | `APP1`/`APP13`/`COM` 段 |
| ISO BMFF（MP4/M4A） | video / audio（按主品牌） | `moov` / `meta` / `uuid` box（`mdat` 按尺寸跳过） |

**载荷形态**（附录 E b)：`{外层包裹键: {要素键: 字符串值, …}}`）。外层包裹键从映射表的
`parse_profile.payload_wrapper` 读（**数据驱动，不在代码里硬编码政策键名**）；要素键由
映射表别名识别。解析器只做"找 JSON → 摊平外层 → 交出键值字典"。

**确定性**：纯 stdlib、无时钟/随机；`card_id` 由**内容 sha256 派生**（`PARSED-<16 hex>`），
同字节文件 → 同标识卡 → 同报告（逐字节一致）；键序 = 发现顺序。

**降级纪律（硬要求）**：解析不到就**显式降级**，绝不臆测——

| 情形 | 原因码 | 隐式作用域 |
|---|---|---|
| 容器结构截断/畸形 | `structure_broken` | 未观测 → 全部 `unknown` |
| 容器类型不可识别 | `unsupported_container` | 未观测 → 全部 `unknown` |
| 结构完整但无 AIGC 载荷 | `no_aigc_payload` | **已观测**（确实缺失）→ `presence` 判 fail |
| 映射表未配置解析画像 | `no_payload_wrapper_configured` | 未观测 → 全部 `unknown` |

**显式标识作用域恒为未观测**（解析器看不到渲染后的文字/语音）。

**为什么解析通路不用完整 JPEG/PNG 库**：核心层零第三方依赖（D05）；且我们只要**元数据段**，
结构解析（块/段/box 遍历）用 stdlib 的 `struct`+`zlib` 足够，并能在结构坏时**如实降级**
（第三方库可能抛异常或静默容错，都不如显式降级可测）。

## 六、完整性判定与分级（`engine/integrity.py`）

输入：显式 Findings + 隐式 Findings。输出 `grade` + `missing` + `errors`。

**分级算法（定稿）**：

```
设 fails = { f | f.status == fail }；assessed = { f | f.status != skipped }
若 card 输入非法（已在入口拦截）→ 不进此函数
若 assessed 为空（无 Finding，或全部 skipped）→ "not_assessed"
若 fails 为空：
    unknowns 非空 → "partial"（无明确违规，但有待人工确认项）
    否则         → "compliant"
若 fails 非空：
    按 severity 聚合：
      存在 critical/major 级 fail → "non_compliant"
      否则（仅 minor 级 fail）     → "partial"
grade 一律附 missing（fail 的 target 列表）+ errors（fail 的 code 列表）
```

- **`not_assessed` 的两条来路**（都表示"没检查"）：① 规则库条目全 `pending`（M0 可观测行为）；
  ② 当前载体/场景下**没有一条规则适用**（全部 `skipped`）。**"没检查"绝不输出成"合规"。**
- `skipped` 不参与分级（不适用 ≠ 合规 ≠ 违规）。
- "必需规则"由规则条目的 `severity=critical` 标记（不引入第二套"必需"概念）。
- 边界情形（**01 §三.3 明确要求显式处理**）：**元数据被剥离但显式标识在** → 隐式字段全 `fail`、
  显式全 `pass` → 若隐式缺失含 critical → `non_compliant`；否则 `partial`，`missing` 列出被剥离字段。
  该情形**必须进基准枚举**（M4），M2 已在解析算例中给出对应例（`PARSE-PNG-0007`）。

## 七、批量扫描与对账（`scan/`，M3）

- **输入**：目录（递归收集 `*.json` 标识卡 **与** PNG/JPEG/MP4/M4A 容器）或清单文件
  （每行一个路径，`#` 起始为注释）；也接受单文件。
- **逐件分派单点**：每件经 `engine.check_file`（与 `check` 单件**同一**分派）——
  JSON 卡 → 标识卡通路；否则按容器魔数走解析通路；两者皆不是 → 该件记失败（批量不中断）。
- **失败隔离**（NFR-8）：单件异常（坏 JSON、非法卡、不可解析容器、读盘失败、超大容器）
  捕获为 `kind="failed"`（`code=scan_error` / `container_too_large`），记入结果并**继续**；
  失败件是"未判定"（不计违规、不计入 `fail_targets`）。
- **安全阀**：容器件超过 `MAX_CONTAINER_BYTES`（默认 512 MiB）**不整体读入**，按
  `container_too_large` 跳过（防一个超大文件拖垮整批）。
- **进度**：每 N 件向 **stderr** 打一行（`--quiet` 关闭；stdout 不被污染）。
- **产出**：`ScanResult{ items, summary, failed, ruleset }`（`to_dict` 顺序固定 → 可复现）。
- **对账（FR-7）**：输入上轮与本轮 `ScanResult`，做四类集 + 内容变动标记：
  - **新增违规** `added`：本轮 fail 而上轮非 fail（或上轮无此件）；
  - **已修复** `fixed`：上轮 fail 而本轮非 fail；
  - **持续违规** `persistent`：两轮均 fail（`changed_targets` 记 fail 目标集变化）；
  - **稳定** `stable`：两轮均无 fail；辅助集 `new_items`（新增且合规）/`removed`（本轮消失）。
  - **配对主键 = 稳定身份键**（`ScanItem.identity`，**口径见 plan/06 D28**）：
    标识卡件 `card:<card_id>`（逻辑身份，与文件名/内容无关）、解析件/失败件
    `file:<相对路径>`（路径稳定）。**不用**内容指纹作主键——解析件 `card_id` 由内容派生，
    按它配对会让"已修复"永远检不出。
  - **指纹变化单独记** `content_changed`（身份不变而 `content_sha256` 变）：如实标出
    "内容被改动"，**不**退化成"新增 + 移除"。

## 八、报告与证据链（`report/`，M3）

### 8.1 报告结构（固定骨架）

1. **报告头**：标题、生成时间（**由调用方传入**，基准/测试传固定值）、**规则库坐标**
   （doc × version + sha256）、`verified/pending` 规则计数、扫描根；
2. **免责声明**（强制段，不可省略）；
3. **核查范围**：件数、载体分布、数据来源、等级分布、**适用场景**、**未观测作用域**、
   **解析降级件与原因码**（M2 口径必须进报告，否则解析件会被误读成"显式合规"）；
4. **依据清单**：每条挂文号/标准号 + 施行日 + 版本（取自 `registry`，单一来源）；
5. **逐件逐字段结果**：表格（件 id、载体、要素/字段、status、severity、原因码、条款）；
6. **违规清单**：按 severity 排序（critical → major → minor）；
7. **失败件清单**（失败隔离的可观测输出）；**两轮对账**段（传入 diff 时）；
8. **结论与建议**：分级汇总。

### 8.2 导出格式

| 格式 | 依赖 | 降级 |
|---|---|---|
| Markdown（`report.md`） | 无 | — |
| CSV（`summary.csv` 每件一行 / `detail.csv` 每 finding 一行） | 无 | — |
| XLSX（`report.xlsx`） | `openpyxl` | 缺失 → 打印安装提示，导出 CSV（exit 0，不崩） |
| 证据（`evidence.json`） | 无 | — |

### 8.3 证据链（FR-9 / 系列招牌）

- 每件内容 `content_sha256` 随结果固化（进 `evidence.json.items`）；
- `evidence.json` 含 `{ruleset_coordinate, generated_at, report_sha256, artifacts{name→sha256},
  summary, items, disclaimer}`；
- **报告自身 sha256** 写入证据文件 → 报告被改动即可检出（对照复现）。`generated_at` 由调用方传入，
  故**两次相同输入的导出逐字节一致**（守门测试）。
- **XLSX 确定性**（plan/06 D29）：openpyxl 写入的文档属性时间戳与 zip 条目时间戳**全部钉死**
  （`generated_at` 可解析时用之，否则固定基准），否则间隔 1 秒导出即字节不同。

### 8.4 退出码（M3 补充）

`scan` 沿用 0/1/2/3：**任一件检出 fail → 1**；失败件（`scan_error`）**不**影响退出码
（它是"未判定"而非"违规"，见 plan/06 D30）。用法/环境错误同 `check`（2/3）。

## 九、内置评测基准（`benchmark/`，M4）

| 基准 | 内容 | 指标（达标线） |
|---|---|---|
| `fields` | 逐 `check_type` 的枚举用例（存在性/位置/格式/取值/类型/唯一性/场景门控），含**边界与畸形输入** | 判定准确率（100%） |
| `constructed` | 程序化构造带**已知标识配置**的合成件（正确/缺字段/错取值/错格式/错位置/元数据剥离/显式缺失/重复保留/场景义务/未观测） | 检出率（≥0.95）/ 误报率（=0） |
| `diff` | 两轮扫描差异对账的确定性验证 | 对账集合一致率（100%） |

- 三类 runner 一条命令跑全（CLI `bench`），退出码 `0` 达标 / `1` 未达标 / `2` 用法错误；
  **全量单次 <1 秒**（实测 0.12 s）。
- 指标写进 README 表格（可信度核心证据），并由 `tests/test_benchmark_runner.py` 锁死。
- **零 API 依赖**（纯规则通路）；`benchmark/` 模块零第三方顶层依赖（AST 守门）。

### 9.1 模块划分（`src/labelcheck/benchmark/`）

| 模块 | 职责 |
|---|---|
| `cases.py` | **单一实现源**：对账口径（`observed_nonpass`/`compare_nonpass`）+ 三类算例构造 + 用例判定 |
| `metrics.py` | `Metric`（值 + 方向 `>=`/`<=` + 阈值）、`SuiteResult`、`BenchReport`；`rate` 的空分母口径显式 |
| `runner_fields.py` / `runner_constructed.py` / `runner_diff.py` | 三类 runner（各产出 `SuiteResult`） |
| `__init__.py` | `run_benchmark(data_dir, only=None, work_dir=None) -> BenchReport`；`BENCH_NAMES` |

### 9.2 对账口径（**唯一实现**，与真值库测试同源）

对账按 `expected` 声明的**非 pass 集合**与引擎实际非 pass 集合比对（plan/05 §三.2）：

- **非 pass = `fail` ∪ `unknown`**（同一 target 的两种状态合并为一个目标）；
- **未观测的 scope 排除在比较之外**——引擎对其一律判 `unknown`，那是"没看到"而非"缺失"
  （解析通路的显式作用域恒为未观测；若把它算进比较，11 例解析算例会全部假失败）；
- `tests/test_generators.py`（标识卡真值库）与 `tests/test_parse_regression.py`（容器算例）
  与基准**共用** `benchmark.cases` 的这两个函数——杜绝"基准说达标、测试说不过"的双口径。

### 9.3 指标方向（**显式**，不靠单一 `>=` 糊过）

| 指标 | 方向 | 阈值 | 说明 |
|---|---|---|---|
| 判定准确率 | `>=` | 1.0 | 全部为确定性用例，无"统计意义上的接近" |
| 检出率 | `>=` | 0.95 | 分母 = 有注入的用例；分子 = 引擎 fail 目标集与注入期望**完全一致**的用例（多报/少报都算未检出） |
| 误报率 | `<=` | 0.0 | 分母 = 无注入的用例；**硬口径**——把合规件判成违规是工具的致命错误 |
| 对账集合一致率 | `>=` | 1.0 | 全部对账集合（含辅助集合）逐件一致 |

### 9.4 算例来源（**复用既有真值，不另造一套**）

- `data/truth/`（8 例标识卡）+ `data/parse/fixtures.json`（11 例容器）是现成算例，各自的
  回归测试仍逐例跑；基准另按 `check_type` 与注入类型**程序化扩展**算例（fields 30 例、
  constructed 34 例（含随附真值库 8 例）、diff 2 场景）；
- 合规取值/位置/枚举**全部从规则库派生**（`valid_implicit_value`/`explicit_element`/
  `pattern_fragments`），源码不含任何规则取值（零政策字面量门覆盖 `benchmark/`）；
- 期望值由**注入点**推出（"注入了 F 缺失 → F 应 fail"），**不许改真值凑引擎**；
- 引擎分支类用例（规则引用字段不在映射表 → `unknown`；无适用规则 → `not_assessed`）
  在**临时合成数据目录**里跑，不污染仓库规则库。

| 守门 | 断言 |

## 十二、桌面界面与打包（`gui/` + `packaging/`，M5）

### 12.1 GUI 分层与"零判定"纪律

```
tabs.py（六页签控件，惰性取 Qt 符号）
   ↓ 只调
services.py（**唯一引擎调用点**，零 Qt、零判定）
   ↓ 只调
engine.check_file / scan.scan_target / scan.diff_scans / benchmark.run_benchmark
```

- **页签**（`gui/tabs.py`）：单件核验 / 批量扫描 / 两轮对账 / 基准指标 / 规则库与依据 / 关于。
  每个页签把"调引擎 + 刷新控件"暴露为普通方法（`check_path`/`scan`/`run`/`refresh`），
  返回**引擎对象**——offscreen 下无需真实交互即可断言（`tests/test_gui_tabs.py`）。
- **服务层**（`gui/services.py`）：**零 Qt**、**零判定**。无 PySide6 的机器也能导入，
  故可被普通 pytest 全覆盖。AST 守门断言它不 import 判定器、也不 import PySide6。
- **渲染层**（`gui/format.py`）：引擎字段 → 展示行/文本；等级中文名从 `report.GRADE_LABELS`
  复用（避免第二份口径）。零判定。
- **入口**（`gui/main_window.py`）：主窗口装配 + 数据目录下发；**顶层 import PySide6**
  （在 `gui/` 豁免名单内）。CLI 侧 `gui` 子命令**函数体内**惰性导入本模块。

**为什么这样切**：把"调引擎"与"画控件"分开，界面逻辑就只可能在服务层出错，而服务层
零 Qt 可被普通 pytest 全覆盖；同时界面与 CLI 共用同一编排入口，杜绝"界面一套、命令行另一套"
的口径分叉（同 plan/06 D32 的动机）。

### 12.2 打包：onedir 双 exe + 白名单内嵌数据

| 产物 | console | 用途 |

  冻结态标记为真、生效规则数 > 0。GUI exe 在无显示环境会崩，故冻结态实跑用 CLI exe。
