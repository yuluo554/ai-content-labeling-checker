## 一、痛点 → 能力转译

| # | 现实痛点 | 转译后的能力 | 落点模块 | 优先级 |
|---|---|---|---|---|
| 1 | 我产出的内容"标识到底合不合规"没有确定性口径，靠人肉读办法与强标 | **规则库驱动的确定性核验**：办法/国标条款编码为可执行规则，结论挂条款依据 | `rules` + `engine.explicit` | P0 |
| 2 | "有没有标识"好判，"位置/形式对不对"难判（开头/显著位置/起始提示） | **显式标识要素级判定**：逐要素判 `present` + `position/form` 合规 | `engine.explicit` | P0 |
| 3 | 隐式标识藏在元数据里，字段名与格式各容器不一，肉眼不可见 | **元数据字段级核验** + **字段映射引擎**（容器键 → 国标字段） | `engine.implicit` + `mapping` | P0 |
| 4 | 单件结论无意义，"缺哪些、错哪些"要成表才能整改 | **完整性判定与分级**：完全合规/部分合规/不合规 + 缺失项/错误项清单 | `engine.integrity` | P0 |
| 5 | 平台侧内容量以千计，逐件点开不现实 | **批量扫描引擎**：目录/清单投喂、失败件隔离、进度可见、结果导出 | `scan` | P1 |
| 6 | 整改是循环的，"这轮比上轮好了没"需要客观对账 | **两轮扫描对账**：新增违规 / 已修复 / 持续违规 | `scan.diff` | P1 |
| 7 | 核查结论要能交给同事/监管/存档，口头说没用 | **合规报告导出**（Markdown + XLSX），含范围/依据/逐件逐字段/结论 | `report` | P1 |
| 8 | 报告可能被改，结论要能复现对照 | **证据固化**：每件内容指纹（sha256）+ 核验记录随报告固化 | `report.evidence` | P0 |
| 9 | 规则会变（新规/修订），旧结论要用旧口径复现 | **版本化规则库**：按 `依据文件 × 版本` 组织，切换即切口径；报告头固定输出规则库坐标 | `rules` | P0 |
| 10 | 规则库若是"拍脑袋写的"，工具本身就是合规风险 | **status 门控 + 逐条挂原文出处**：未核对（`pending`）不得进入判定路径 | `rules.gate` | P0 |
| 11 | 没有标注数据，核验正确性无法证明 | **内置评测基准（零 API）**：字段规则基准 + 构造真值基准 + 批量对账基准 | `benchmark` | P1 |
| 12 | 用户要能双击就用，不是装 Python 跑脚本 | **桌面 exe + CLI 双形态** | `gui` + `packaging` | P1 |

### 差异化（对应 01 §五"开源空白"）

合规口径的核查工具近乎空白，且高 star 项目集中在**去水印/反合规**方向。本工具的差异化不在"识别水印算法"，而在
**"以中国办法 + 强制性国标为规则源，把合规判定做成可执行、可版本化、可批量、可留证据的确定性核验"**。

## 二、功能需求（FR）清单

> 编号 `FR-x` 与 01 §二 的 1)–7) 对应。每条给**验收指向**（哪份文档/哪类测试证明它成立）。

| 编号 | 需求 | 输入 | 输出 | 优先级 | 验收指向 |
|---|---|---|---|---|---|
| FR-1 | 显式标识要素核验 | 结构化标识卡（人工录入）或解析出的载体信息 | 逐要素 `present` + `position` 判定 + 条款依据 | P0 | 04 §四；`tests/test_engine_explicit.py` |
| FR-2 | 标识位置/形式合规判定 | 同上（`position` 字段） | 位置是否落在规则允许集内；不合规给原因 | P0 | 04 §四；同上 |
| FR-3 | 隐式标识字段核验 | 标识卡的 `implicit` 字段字典 | 逐字段 存在性/类型/格式/取值 判定 + 条款依据 | P0 | 04 §五；`tests/test_engine_implicit.py` |
| FR-4 | 字段映射引擎 | 容器元数据键值 + 映射表 | 归一到国标字段名（含别名/扩展键） | P0 | 04 §五；`tests/test_mapping.py` |
| FR-5 | 标识完整性判定与分级 | 显式 + 隐式核验结果 | 合规等级 + 缺失项/错误项清单 + 挂条款 | P0 | 04 §六；`tests/test_engine_integrity.py` |
| FR-6 | 批量扫描 | 目录（多份标识卡/载体） | 合规总表 + 逐件明细；失败件隔离不中断 | P1 | 04 §七；`tests/test_scan.py` |
| FR-7 | 两轮扫描对账 | 上轮结果 + 本轮结果 | 新增违规 / 已修复 / 持续违规 | P1 | 04 §七；`tests/test_scan_diff.py` |
| FR-8 | 合规报告导出 | 单件或批量核验结果 | Markdown + XLSX（范围/依据/逐件逐字段/违规清单/结论） | P1 | 04 §八；`tests/test_report.py` |
| FR-9 | 证据链固化 | 被核查内容 | 每件 sha256 指纹 + 核验记录随报告固化；报告头输出规则库坐标 | P0 | 04 §八；`tests/test_evidence.py` |
| FR-10 | 版本化规则库 | 依据文件 × 版本 | JSON 规则库；`pending` 条目不得生效；切换即切口径 | P0 | 04 §三；`tests/test_rules_gate.py` |
| FR-11 | 内置评测基准 | 合成样本 + 真值 | 解析/核验/对账三类指标（零 API 可重复） | P1 | 04 §九；`tests/test_benchmark_*.py` |

### FR-1/FR-2 的输入形态（重要边界）

题目要求"输入支持结构化描述（人工录入元信息）+ 文件解析（可解析的载体自动提取）"。**首期把两者做成同一中间表示的两条来源通路**：

- **结构化通路（M0–M2 主线）**：用户/上游系统给出**标识卡 JSON**（载体类型、显式要素清单、隐式字段字典、内容指纹）。确定性、可测、可基准。
- **文件解析通路（M2 起增强）**：对可解析载体自动提取（文本文件头部/尾部文本、图片/音视频容器的元数据段），产出同一标识卡。解析失败**不静默**，降级为"解析不可用 + 原因"，由人工补录或直接判 `unknown`。

> 覆盖不到的情形一律显式落 `unknown`/`unparsed`，绝不臆测为合规。

## 三、非功能需求（NFR）

| 编号 | 要求 | 口径与验证 |
|---|---|---|
| NFR-1 | **全本地、零上传** | 无任何网络调用；核心层零第三方依赖（纯 stdlib）；测试断言源码无 `requests`/`urllib.request`/`socket` 直连 |
| NFR-2 | **零 LLM 依赖** | 结论 100% 由确定性规则产生；决策记录显式记"LLM 使用：不使用"（无解析兜底需求，见 06） |
| NFR-3 | **确定性可复现** | 规则库为生成器冻结产物，禁手改；两次运行/构建**逐字节一致**；自研确定性 RNG（splitmix64），禁 stdlib `random`、禁 set 迭代序、禁系统时钟进产物 |
| NFR-4 | **未核对不得生效** | 规则条目 `status ∈ {verified, pending}`；`effective_ruleset()` 单点门控拒绝 `pending` 进入判定路径 |
| NFR-5 | **零政策字面量** | 规则库中的数值/格式约束收编为禁用 token，对引擎/基准/前端源码扫描（含 docstring/注释）；豁免口径写死（<100 整数=日历/精度常数） |
| NFR-6 | **跨平台** | Windows 与 Linux 行为一致；`src` 布局 + 可编辑安装；CI 双 OS 矩阵（`windows×3.12` + `ubuntu×3.12`；2026-10-19 D-1/D44 去 3.8） |
| NFR-7 | **无 Python 环境可跑** | PyInstaller onedir 双 exe（GUI + CLI console）；冻结态数据定位经 `find_data_dir` 分支测试锁定 |
| NFR-8 | **失败隔离** | 批量扫描中单件异常不中断整批；CLI 退出码语义锁定（见 04 §二） |
| NFR-9 | **线索可读** | 每条判定挂条款依据（文号/标准号 + 条号；未核对时显式标 pending 占位，不得编造条号） |

## 四、边界守卫（防 scope 失控）

### 4.1 明确不做（对应 01 §六"非目标"）

| 不做项 | 原因 |
|---|---|
| ❌ 去水印 / 标识移除 / 标识规避（含任何"通过核验的技巧"） | 反合规，伦理红线；README 与技术报告显著声明 |
| ❌ 特定厂商私有水印算法逆向 / 破解 | 不具正当性，且非合规口径 |
| ❌ 法务定性结论（"违法/不违法"） | 工具是合规辅助；结论供参考，正式认定以监管口径为准 |
| ❌ 对接平台举报接口 / 自动处置 | 越权对外动作 |
| ❌ 收录真实平台内容 / 真实个人信息 / 真实商业素材 | 数据纪律；样本全为合成虚构 |
| ❌ 云端核查 / 内容上传 | 被核查内容可能含商业敏感信息 |

### 4.2 首期范围（收口）

- 依据：**《标识办法》+ GB 45438-2025**（其余上位规章条文入库为"参考依据"，不作为首期判定依据，待核对后按版本启用）。
- 载体：**文本 / 图片 / 音视频** 三类标识字段规范。其余载体（如特定行业叠加要求）留扩展位。

### 4.3 易失控点与守卫

| 失控风险 | 守卫 |
|---|---|
| "顺便做个去水印检测吧" | 非目标清单进 README + 拒绝在 `engine` 中引入任何像素/信号处理依赖 |
| 规则库越写越大、真假混入 | `status` 门控 + 每条挂出处 + `data/README.md` 台账登记 sha256 |
| 解析通路无底洞（各种容器格式） | 首期只做"标识卡"主通路；解析通路按载体逐类增量接入，失败显式降级 |
| 报告变成"合规证书" | 报告头强制免责声明段；结论措辞固定为"核查结论"而非"认定" |

## 五、受众与使用场景

| 受众 | 场景 | 主通路 |
|---|---|---|
| AIGC 服务提供者 | 上线前自检产出内容的标识完备性 | CLI `check` 单件 / GUI 单件页签 |
| 内容平台合规岗 | 批量抽检收到的内容标识完整性 | CLI `scan` + 报告导出（CSV/XLSX） |
| 企业内容合规岗 | 整改循环跟踪（这轮比上轮修好了哪些） | 两轮扫描对账 + 报告证据链 |
| 研究者 / 开发者 | 复现评测指标、扩展载体规则 | `benchmark` + 规则库版本化扩展 |
