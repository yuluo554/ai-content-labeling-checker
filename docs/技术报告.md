# 技术报告：AI 生成合成内容标识合规核查器

> 本报告说明**标识规则化方法、元数据映射设计、批量与证据链、内置基准指标**四块技术核心，
> 以及"为什么这样做"的取舍。所有数值口径都能在仓库里复现（每条都给了命令）。

**工具定位**：以《人工智能生成合成内容标识办法》（国信办通字〔2025〕2 号）与强制性国家标准
GB 45438-2025《网络安全技术 人工智能生成合成内容标识方法》为规则源，对内容标识做
**显式要素核验 + 隐式元数据字段核验 + 完整性分级**，支持批量扫描与合规证据链导出。
全本地核查、零上传、零 LLM 依赖——结论由确定性规则产生，100% 可复现。

**免责声明**：本工具为合规辅助，结论供参考，正式合规认定以监管口径为准；
**不提供任何去水印/标识规避功能**。

## 一、标识规则化方法：把"法规文本"变成"可执行、可核对的规则库"

法规与标准是**自然语言**，工具要给出可复现结论，必须先把它们变成**结构化、带出处、
带核对状态**的规则条目。这是本项目与"调个模型读一遍文件"最本质的区别。

### 1.1 规则库 schema（版本化 × 门控）

规则库落在 `data/rules/<doc_id>/<version>.json`，由 `data/rules/registry.json` 登记
（文号/标准号、施行日、版本、**sha256**）。单条规则的关键字段：

| 字段 | 作用 |
|---|---|
| `scope` | `explicit`（渲染可见标识）/ `implicit`（文件元数据标识） |
| `target` | 被核验的要素或字段 id（**不写具体取值**） |
| `check_type` | 判定类型：`presence`/`position`/`enum`/`pattern`/`type`/`range`/`unique` |
| `params` | 判定参数（允许位置集、枚举值集、正则片段、类型名……） |
| `carrier` | 载体门控（空 = 全部载体；如"图片位置=边或角"只对 `image` 生效） |
| `only_if.scenario` | **场景门控**（`authored`/`exported`/`propagated`） |
| `severity` | `critical`/`major`/`minor`（进分级与违规排序） |
| `clause` | 条号 + 要点摘录（**依据可追溯**） |
| `status` | `verified`/`pending`（**门控开关**） |
| `source_url` / `verified_at` | 出处链接 + 核对日期 |

### 1.2 status 门控：`pending` 绝不进判定路径

**这是本项目的核心纪律**（`plan/03` §六、`plan/04` §三.4）。规则条目必须**逐条挂原文核对**
（条号 + 出处 + 核对日）后才转 `verified`；`effective_ruleset()` 只返回 `verified` 条目。

为什么必须这样：法规条目若凭印象写进判定路径，工具会输出**看似权威、实为编造**的结论——
比"查不出问题"更危险。当前仓库生效 **27 条**（国标 25 条 + 办法 2 条独有义务），
其余 7 条办法条目因"与国标同 target"保持 `pending`（技术判定由国标承担，避免同一目标
跨文档产生双份 Finding）。

```bash
PYTHONPATH=src py -X utf8 -c "from labelcheck.paths import find_data_dir; \
from labelcheck.rules import effective_ruleset; r=effective_ruleset(find_data_dir()); \
print(r.verified_rule_count, r.pending_rule_count, r.coordinate)"
# → 27 7 labeling-measures@2025-09-01
```

### 1.3 适用性画像：不适用记 `skipped`、未观测记 `unknown`

**同一份文件，在不同场景下义务不同**。例如办法第四条第二款要求"导出/下载的文件"含显式
标识，第六条要求"网络信息内容传播服务"发布时加提示——若对产出阶段的内容也套用这两条，
就会把"不适用"判成"违规"，**冤枉用户**。

故引入两个输入契约（`plan/06` D23）：

- **场景** `scenario`：规则以 `only_if.scenario` 声明适用场景，不适用 → `skipped`
  （**不是** `fail`，也不是 `pass`）；
- **观测作用域** `observed`：`observed[scope]=False` → 该 scope 一律 `unknown`
  （解析通路读不到渲染后的画面文字/语音，**绝不臆测**为合规或违规）。

这条画像让 4 条原本 `pending` 的条目有了**正当**的转 `verified` 路径——不是放宽核对，
而是把"这条到底对谁成立"画像清楚了。

### 1.4 唯一性约束（`unique`）与"缺值不臆测"

- GB 45438-2025 §6.1 c) 要求"仅保留一份文件元数据隐式标识"。该约束的对象是**整块**隐式
  标识（同一要素是否被多个容器键/多份副本重复提供），而非单值——故 `unique` 由
  `engine.implicit` 直接判定，不经通用 `evaluate()` 分派。
- **非 `presence` 类规则遇缺值一律 `unknown`**：值都没读到，凭什么说它格式/取值不对？
  这是"缺值不臆测"原则在判定层的落地。

## 二、元数据映射设计：容器键 → 国标字段

现实里的元数据键名五花八门（不同工具写 `ContentProducer`/`AIGC:ContentProducer`/自定义别名），
而国标只规定**要素语义**。映射表把这层"翻译"做成**可配置、可版本化的数据资产**
（`data/mapping/national-fields.json`）。

### 2.1 映射表结构

| 字段 | 作用 |
|---|---|
| `national_field` | 国标要素名（判定目标） |
| `aliases` | 该要素可能出现的**全部容器键**（声明序 = 归一优先级） |
| `status` / `clause` / `source_url` | 同规则库（逐条可追溯） |
| `parse_profile.payload_wrapper` | 附录 E 载荷的外层包裹键（**数据驱动**，不硬编码） |

当前 5 个字段全 `verified`。

### 2.2 归一算法（确定性）

`resolve_fields()` 按映射表**声明顺序**，对每个字段取**第一个存在**的键作主键，
其余命中的键记入 `alternatives`（**不静默丢弃**）。命中顺序由声明序决定，
不看 `set`/`dict` 迭代序 → 跨机器、跨 Python 版本结果一致。

`alternatives` 不是装饰：它正是 §6.1 c) 唯一性判定的输入——同一要素被多个别名键
同时提供 = 隐式标识被重复保留。

### 2.3 标准自身差异的处理（如实保留，不擅自调和）

核对中发现 GB 45438-2025 **附录 E（规范性）** 写作 `ContentPropagator`/`PropagateID`，
而**附录 F（资料性）** 示例写作 `Propagator`/`PropagatorID`。工具的处理是
**两套键名同时登记为别名**（`plan/06` D20），而不是在数据层"二选一"——
标准自身表述不一致是客观事实，工具如实覆盖，而不是把它固化成判定口径。

## 三、批量与证据链

### 3.1 两条输入通路，共用一处分派

| 通路 | 输入 | 特点 |
|---|---|---|
| **标识卡通路** | 结构化 JSON（人工/上游系统录入） | 显式 + 隐式都可信（两个 scope 均"已观测"） |
| **解析通路** | PNG/JPEG/ISO BMFF 容器文件 | 只读元数据 → 隐式；显式作用域**恒为未观测** |

关键设计：`check`（单件）与 `scan`（批量）**共用** `engine.check_file` 一处分派
（`plan/06` D32）。两条通路若各写一套分派，同一文件在单件与批量下会给出不同结论——
这是最隐蔽的口径漂移。解析器为**纯 stdlib 结构解析**（PNG 块 / JPEG 段 / ISO BMFF box），
结构坏/无载荷即**显式降级**为 `unknown` + 原因码，绝不臆测。

### 3.2 批量扫描的失败隔离

一个坏文件不该毁掉整批。`scan` 对单件异常（坏 JSON、非法卡、不可解析容器、读盘失败、
超大容器）记一条 `kind="failed"` 记录后**继续**；失败件是"未判定"，**不计违规**、
**不影响退出码**（`plan/06` D30/D31）。退出码因此是干净的两分：`1` = 检出违规
（脚本按码分流），`3` = 环境问题。

### 3.3 两轮对账：主键必须是**稳定身份键**

这是本项目对账设计里最容易踩的坑。解析件的 `card_id` 由**内容哈希派生**——内容一变
id 就变。若一律按 `card_id` 配对，那么：

- "同一文件被改动" → 误判成"新增 + 消失"；
- **"已修复"永远检不出来**（修复 = 内容变了 = id 变了）。

故为每件定一个**稳定身份键**（`plan/06` D28）：

| 件类型 | 身份键 | 理由 |
|---|---|---|
| 标识卡 JSON | `card:<card_id>` | 逻辑身份，与文件名/内容编辑无关 |
| 解析件 / 失败件 | `file:<相对路径>` | 路径稳定；容器内容可改而路径不变 |

内容指纹 `content_sha256` **不参与配对**，只用于独立标记 `content_changed`——
"内容改了但身份不变"被如实标出，而**不**退化成"新增 + 移除"。对账产出四类集合
（新增违规/已修复/持续违规/稳定）+ 辅助集合，全部顺序固定。

### 3.4 证据链（可对照复现）

一次导出产出 `report.md` / `summary.csv` / `detail.csv` / `evidence.json`（+ 可选 `report.xlsx`）。
`evidence.json` 固化每件 `content_sha256`、规则库坐标（含 sha256），并写入**报告自身的
sha256**——报告被改动即可检出。产物**无时间戳**（`generated_at` 由调用方传入）→
**相同输入两次导出逐字节一致**，这是"可复现"的硬保证，也有守门测试锁死。

XLSX 另有一处坑：openpyxl 默认把文档属性时间戳与 zip 条目时间戳写成当前系统时刻，
间隔 1 秒导出即字节不同。处置是把两者**全部钉死**（`plan/06` D29）。

## 四、内置评测基准：核验正确性的可复现证据

"没有标注数据，核验正确性无法证明。" 本项目把正确性做成**可重复、零 API、零外部依赖**
的指标，一条命令跑全。

### 4.1 三类基准

| 基准 | 内容 | 指标 | 达标线 |
|---|---|---|---|
| `fields` | 逐 `check_type` 的枚举用例（存在性/位置/格式/取值/类型/唯一性/场景门控），含**边界与畸形输入** | 判定准确率 | 100% |
| `constructed` | 程序化构造带**已知标识配置**的合成件 | 检出率 / 误报率 | ≥ 95% / = 0 |
| `diff` | 两轮扫描差异对账的确定性验证 | 对账集合一致率 | 100% |

### 4.2 本仓库实测（2026-10-13，仓库真实规则库 + 随附算例）

| 基准 | 指标 | 实测 | 达标线 |
|---|---|---|---|
| `fields` | 判定准确率 | **100%**（30/30） | 100% |
| `constructed` | 检出率 | **100%**（23/23） | ≥ 95% |
| `constructed` | 误报率 | **0%**（0/11） | 0（硬口径） |
| `diff` | 对账集合一致率 | **100%**（2/2） | 100% |

全量单次 **0.209–0.236 s**（本机 py3.12 进程内 5 次实测；**参考值，随机器变化**。旧文档的 0.12 s
未能复现，已作废）。

```bash
PYTHONPATH=src py -X utf8 -m labelcheck bench       # 退出码 0 达标 / 1 未达标 / 2 用法错误
PYTHONPATH=src py -X utf8 -m labelcheck bench --json
```

### 4.3 三条设计纪律（让指标可信，而非自证自话）

1. **对账口径唯一实现**：非 `pass` = `fail ∪ unknown`；**未观测的 scope 排除在比较之外**
   （解析通路的显式作用域恒为未观测，那是"没看到"而非"缺失"）。实现在 `benchmark/cases.py`，
   真值库测试与基准**共用**同一套函数——杜绝"基准说达标、测试说不过"的双口径。
2. **期望值不抄引擎**：期望由**注入点**推出（"注入了字段 F 缺失 → F 应 fail"）；
   合规取值/位置/枚举**从规则库派生**，故规则库一变基准跟着变——基准对口径漂移**敏感**。
3. **误报率是硬口径 0**：把合规件判成违规比漏检更伤用户信任，故单列为"越小越好"的指标，
   不与准确率混在一个 `>=` 里。

### 4.4 如实记录未覆盖项

`range` 类型的 `check_type` 在生效规则库中**不存在**（M2 建条决策 D27 显式判定"不建"：
核对记录未覆盖的数值阈值 = 编造标准内容）。故 `fields` 基准在 `notes` 里**如实说明**
"该类用例未生成"，不假装覆盖。若将来因新核对记录建了 `range` 规则，基准会自动开始覆盖
（由 `missing_check_types` 驱动）。

## 五、交付形态：桌面界面 + 双 exe

### 5.1 分层：GUI 只渲染，零判定逻辑

```
表现层   cli/（argparse）      gui/（PySide6，六页签）
              └──────── 只调引擎 API ────────┘
编排层   engine/pipeline.py  check_card / check_file（单一编排事实源）
领域层   rules / mapping / parse / engine / model（纯确定性，零第三方）
应用层   scan / report / benchmark
```

GUI 的"干活"链路是 `tabs → gui/services.py → 引擎入口`，**判定逻辑一律不在 GUI 层**。
`services.py` 是唯一引擎调用点，且零 Qt——无 PySide6 的机器也能导入它，故服务层能被普通
pytest 全覆盖（不需要 `QApplication`）。这条纪律由 AST 守门测试锁死。

六个页签与引擎入口一一对应：单件核验→`engine.check_file`、批量扫描→`scan.scan_target`、
两轮对账→`scan.diff_scans`、基准指标→`benchmark.run_benchmark`、
规则库与依据→`rules.effective_ruleset`/`mapping.load_mapping_table`、关于→包内定位与免责声明。

### 5.2 双 exe：GUI（无控制台）+ CLI（可脚本化）

PyInstaller onedir 双 exe：`labelcheck-gui.exe`（`console=False`，双击即用）+
`labelcheck.exe`（`console=True`，可管道取 JSON、可判退出码）。

**内嵌数据走白名单**（`rules`/`mapping`/`truth`/`parse`/`samples`/`knowledge`），
**不**整仓塞 `data/`——避免把本地私有件与报告输出打进发行包。

**构建后必须验伪**：冻结态数据定位有四个分支，其中"环境变量"与"CWD 上溯"都能兜底命中
**仓库** `data/`。若沿用当前环境或从仓库根跑自检，会"验了个寂寞"——exe 在本机看着能跑、
换台机器就崩。故验收脚本必须：① 清 `LABELCHECK_DATA_DIR`；② 以 exe 目录为 CWD；
③ 断言解析到的数据目录**落在 dist 之内**。

```bash
py -3.12 -m tools.build_exe            # 构建 + 自动校验
py -3.12 tools/verify_package.py       # 单独验收（中立环境）
```

## 六、确定性与守门测试

"可复现"不是口号，是被机器锁住的不变式：

| 守门 | 断言 |
|---|---|
| EOL 门 | 冻结数据（`data/**`）出现 CR 即大声失败（跨平台字节一致的前提） |
| 确定性 RNG | 自研 splitmix64 对固定 seed 的金标准序列逐值相等（不用 stdlib `random`） |
| 零时钟 | 引擎/基准源码不得出现 `datetime.now(`/`time.time()`（产物无时间戳） |
| 零政策字面量 | 规则取值不得抄进源码（含 docstring）——只能从数据文件读 |
| 核心层零第三方 | AST 断言除 `gui`/`packaging`/`report` 外不 import 第三方包 |
| CLI 顶层禁 GUI | AST 断言 `cli/` 顶层无 PySide6（无 GUI 环境也能跑 CLI） |
| 服务层零 Qt | AST 断言 `gui/services.py`/`format.py` 无 PySide6，且不 import 判定器 |
| 规则库门控 | `pending` 条目**绝不**出现在 `effective_ruleset()` 输出中 |
| 解析降级 | 结构坏/无载荷 → 显式 `unknown`/原因码，绝不判成 pass 或 fail |
| 退出码语义 | 0/1/2/3 四码各有测试锁死 |
| CI workflow 可解析 | pyyaml 真解析（非法 YAML 会让 GitHub 不建任何 job） |
| 生成器位级一致 | 4 个生成器 `--check` 断言"再生成逐字节一致" |

当前测试规模：**全量 463 项（py3.12，含 GUI + XLSX）**；CI 覆盖 `windows×3.12` + `ubuntu×3.12`
（test / cli-smoke / packaging-guard）+ `windows×3.12` 的 gui-smoke 与 package job。每个跑 pytest 的 job
都有**收集数对账**（test=447、gui-smoke=463、packaging-guard=18），且 CI 安装 `report` extra 使 XLSX
确定性测试真跑（不再"永远 skip"）。

## 七、结论与已知边界

**已达成**：规则库版本化 + status 门控（27 条生效）、显式/隐式/完整性三核验、
字段映射引擎、解析通路（PNG/JPEG/ISO BMFF）、适用性画像、批量扫描 + 失败隔离、
两轮对账（稳定身份键）、报告 + 证据链、三类内置基准（全部达标）、桌面界面 + 双 exe。

**已知边界（如实声明）**：

- 解析通路只覆盖 PNG/JPEG/ISO BMFF 的**元数据**；纯文本文件无元数据容器，不入解析通路；
- 解析通路的**显式作用域恒为未观测**（读不到渲染后的画面文字/语音）→ 相关判定为 `unknown`；
- `range` 类型的规则当前不存在（核对记录未覆盖数值阈值，不编造）；
- 规则库覆盖面以**已核对条目**为准；`pending` 条目不参与判定；
- 本工具结论供参考，正式合规认定以监管口径为准。
